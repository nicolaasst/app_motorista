# MIGRATION_PROGRESS

Estado real da migração, atualizado a cada lote. Uma tela/endpoint só é
marcada `done` depois que `typecheck`, `lint`, `test`, `build` passam e,
quando aplicável, a comparação visual (`scripts/visual-compare.mjs`) não
mostra regressão acima do limiar. Nada aqui é marcado como concluído por
suposição — ver `docs/OPEN_QUESTIONS.md` para as pendências de produto que
bloqueiam algumas fases.

Legenda: `todo` (não iniciado) · `wip` (em andamento) · `done` (concluído e
verificado) · `n/a` (não se aplica a esta linha) · `blocked` (aguardando
decisão externa — ver OPEN_QUESTIONS).

**Vulnerabilidade adicional encontrada nesta fase (`npm audit`):**
`fastify@4.28.1` (dependência de produção) carrega `find-my-way` com uma
vulnerabilidade de DoS via HTTP/2 e dois problemas de spoofing/validação de
schema. A correção exige `fastify@5` (breaking change). Fica registrada
aqui para ser feita junto da Fase 7 (hardening do backend), não junto da
Fase 1 (que é só tooling de frontend).

## Bugs reais corrigidos na Fase 3 (achados ao substituir o dispatcher)

Confirmados por leitura do código antigo de `PageRuntime.jsx` e por teste
end-to-end real (Playwright, fluxo completo login→...→logout→404→/dev, 0
erros de console além do bloqueio conhecido de fontes externas — ver
`docs/OPEN_QUESTIONS.md` item 8). Nenhuma regressão visual (16/16 telas,
diff ≤0.02% no limiar de 2%):

| Arquivo                                | Bug real (não é sobre o mecanismo de dispatch)                                                                                                                                                                                                                                                                                      | Correção                                                                                                                                                                                                                                                                                                             |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/pages/B1RotaDoDiaHome.jsx`        | Os botões "Navegar"/"Ver Detalhes"/"Iniciar Próxima Parada" usavam, via `PageRuntime`, `route.stops[0]` (uma parada já **concluída**) como alvo — nunca a parada #05 realmente exibida como "Próxima" na tela.                                                                                                                      | Passaram a usar `stop05` (já calculado corretamente pela própria página) para navegação e para `startNavigation()`.                                                                                                                                                                                                  |
| `src/pages/C1HistRicoDeRotas.jsx`      | Os 4 cartões de rota concluída navegavam **todos** para o mesmo destino hardcoded (`/historico/ROM-2024-88376`) — um código que nem corresponde a nenhum dos 4 cartões exibidos.                                                                                                                                                    | Cada cartão navega para `/historico/${seu próprio data-code}`.                                                                                                                                                                                                                                                       |
| `src/pages/D1Recibos.jsx`              | Mesmo padrão do C1: os 4 botões de recibo navegavam todos para o mesmo destino hardcoded.                                                                                                                                                                                                                                           | Mantido o único destino real que existe nos dados (`/recibos/receipt-88401`) de forma consistente em vez de depender de correspondência de texto frágil; a causa raiz (nenhum dos 4 recibos exibidos tem um registro real correspondente) é uma lacuna de modelo de dados, registrada abaixo.                        |
| `src/api/index.js` (`jsonFetch`)       | Todo request enviava `Content-Type: application/json` mesmo sem `body` (ex.: `logout`). O Fastify rejeita isso com 400 ("Body cannot be empty..."). Como o logoff antigo no `PageRuntime` chamava `logout()` **sem `await`**, o erro ficava mascarado (a navegação para `/` acontecia de qualquer forma, silenciando a falha real). | `Content-Type` só é enviado quando há `body`. Descoberto porque o novo handler de logoff usa `await logout()` corretamente (não navega antes da limpeza de sessão terminar) — o que expôs o bug em vez de mascará-lo. Confirmado via teste E2E real (login→…→logout completo).                                       |
| `src/pages/A2EsqueciMinhaSenhaOtp.jsx` | O formulário de OTP/nova senha não tinha `onSubmit`, então o clique no botão `type="submit"` causava um **reload completo da SPA** (submit HTML nativo para a própria URL).                                                                                                                                                         | `onSubmit` com `preventDefault()`. O fluxo de verificação de OTP real (chamar o backend, aplicar a nova senha) ainda não existe — nem no cliente (`src/api/index.js` não tem `otpVerify`) nem no backend (não há endpoint para efetivamente trocar a senha). Registrado como pendência real de Fase 5, não simulado. |

**Lacunas de modelo de dados encontradas (não corrigidas nesta fase — são
Fase 6, "migração tela por tela", que é onde cada tela passa a consumir
dados reais em vez de conteúdo estático):** `C2DetalheDeRotaConcluDa.jsx`,
`D1Recibos.jsx` e `D2DetalheDoReciboComAssinatura.jsx` exibem conteúdo
inteiramente estático (não lêem de `route`/`history`/`receipts` do
`AppContext`) e os 4 romaneios de `C1`/`D1` não têm registro correspondente
em `history`/`receipts`. Validar `routeId`/`receiptId` inválido → 404 real
exigiria essa ligação de dados primeiro (um 404 sem dados reais para
comparar não protegeria nada) — por isso não foi implementado agora de
forma superficial. Fica registrado aqui, não silenciado.
